Implementation guide

Build guide · data lineage · model card

What is happening,
step by step.

This guide connects the challenge brief to the code: which data we create, how features are produced, why the model was chosen, how it is evaluated, and how a score becomes a payment decision.

Competition alignment: this is a hackathon with no supplied dataset. FraudGuard therefore creates its own safe, traceable synthetic payment dataset and is judged on attack diversity, simulation fidelity, detection efficacy, novelty, and real-world feasibility.
1. Problem 2. Identify 3. Dataset 4. Features 5. Model 6. Evaluation 7. Decisions 8. Learning loop
STEP 01

Translate the brief into one closed loop

The challenge asks teams to identify emerging GenAI-enabled payment fraud, generate faithful simulations at scale, and defend against them with accurate AI/ML while limiting false positives. FraudGuard treats these as one loop instead of three disconnected demos.

Creative work stays offline: threat research, scenario mutation, dataset generation, and training. The live payment path stays deterministic: feature calculation, model inference, policy thresholds, and auditable reason codes.

STEP 02

Identify a broad attack landscape

The current catalog contains ten structured families: account takeover, card-not-present bursts, mule networks, bot testing, refund abuse, urgent instant-payment scams, synthetic identity, transaction layering, promotion abuse, and friendly fraud.

Each scenario has a stable ID, severity, version, and observable signals. These are defensive simulation specifications—not instructions for interacting with victims, credentials, or real payment rails.

STEP 03

Create the dataset we need

There is no Kaggle dataset for this challenge. The project generates 9,000 fictional training transactions from nine attack families using fixed seeds. Generator version synthetic-1.1 adds controlled benign hard negatives, probabilistic attack signals, monotonic timestamps, and explicit row profiles alongside provenance and labels.

STEP 04

Turn transactions into behavior

The same FeatureEngine runs during dataset export and API inference, reducing training-serving skew. It produces eleven signals: one-hour velocity, amount deviation, new device, shared-device count, location shift, new payee, card-not-present, unusual hour, new account, identity mismatch, and merchant risk.

Transactions are processed in time order because velocity and novelty only make sense relative to prior customer activity.

The NumPy trainer standardizes every feature, balances fraud and legitimate examples, applies L2 regularization, and selects a validation threshold under a false-positive constraint. The artifact stores weights, normalization, threshold, scenario manifest, metrics, feature version, limitations, and a content-derived model version.

STEP 06

Measure detection and customer friction

On the harder locked test split, precision is 0.749, recall is 0.756, and F1 is 0.752. On unseen transaction layering, the ensemble reaches F1 0.762 versus 0.667 for fallback and recall 0.877 versus 0.590, while false-positive rate rises from 5.8% to 13.8%. The dashboard makes that tradeoff explicit.

We report precision, recall, F1, false-positive rate, confusion matrix, latency, model version, and scoring mode. The dashboard can run both ordinary replay and the novel-family comparison.

STEP 07

Convert risk into an explainable action

The runtime blends 70% model probability with 30% transparent rule score. Configurable thresholds map the result to ALLOW, STEP_UP, REVIEW, or BLOCK. Every response includes probability, rule score, human-readable reason codes, feature/model versions, and latency.

If the model artifact is missing or invalid, scoring continues in SAFE_FALLBACK mode using deterministic rules. Generative AI is never placed in the synchronous payment decision path.

STEP 08

Use errors to harden the next defense

Outcome feedback is classified as correct, false positive, or false negative. The learning endpoint now replays an unseen scenario, selects actual false negatives, and creates traceable amount, payee, device, and merchant-context stress variants. Every batch is marked HUMAN_REVIEW_REQUIRED: it never retrains, changes, or promotes the active model. The next milestone trains an isolated candidate artifact from approved variants and shows locked before/after evidence.
